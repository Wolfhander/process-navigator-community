# Участие в разработке

1. Сначала обсудите существенное изменение в Issue: задачу пользователя, ожидаемый результат и ограничения.
2. Не прикладывайте рабочие процессы, структуры предприятий, персональные данные и ключи. Используйте синтетический пример.
3. Добавьте проверку поведения и обратной совместимости, затем соберите интерфейс и сервер.
4. Для изменения модели проверьте просмотр, редактор, API, Excel и расчёт сроков по затронутым функциям.
5. Не представляйте структурную проверку как доказательство смысловой корректности процесса.
6. Документацию и историю решений обновляйте после законченного связанного этапа, не для каждого небольшого изменения.
7. GitHub Release и релизный тег создавайте только по прямой просьбе владельца проекта. Обычный завершённый пакет можно коммитить и отправлять в `main`, но это не повод создавать или перевыпускать релиз. Обновление истории версий внутри программы не является GitHub Release.

Перед отправкой кода учитывайте, что лицензия проекта пока не выбрана. Не добавляйте чужие материалы, для которых нет разрешения на публикацию.
