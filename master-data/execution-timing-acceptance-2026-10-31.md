# Приёмка фактического времени — 31 октября 2026

Пункт 51. Общий рабочий синтетический набор execution-timing-fixture.json читается напрямую серверными и клиентскими проверками: очередь, пауза, возобновление, отмена, null-норматив, сохранённый факт завершения, пропуск и старая отмена без даты остановки.

## Методика

Время шага — активные календарные минуты от доступности: очередь до начала плюс работа от начала до завершения/среза, за вычетом пауз экземпляра. День норматива по прежнему правилу — 8 часов, но это не применение производственного календаря. При возобновлении сдвигается нормативная дата, не отдельный базовый план. На паузе дата может оставаться в прошлом без роста активной просрочки. Отмена замораживает незавершённое время по событию; при отсутствии такого времени результат неизвестен, не нулевой.

Сохранённые факты завершения имеют приоритет. Пропущенный шаг не объявляется выполненным. Нулевой, отрицательный, отсутствующий или нечисловой норматив не задаёт нулевой SLA. Серверная аналитика считает превышение доступной очереди, исключает отменённые шаги из текущей работы и сохраняет превышение к моменту остановки. Среднее шага включает очередь и работу без пауз; календарный цикл экземпляра от запуска до завершения включает паузы.

Карточка рассчитывает оперативную оценку по часам устройства и обновляется раз в 30 секунд для доступной очереди/работы. Серверная аналитика фиксирует время UTC; часы клиента не считаются автоматически синхронизированными. Перезагрузка получает новый срез; поздний ответ прошлого процесса игнорируется.

## Проверки

ExecutionTimingChecks проверяет девять общих случаев (включая одинаковое округление дробных минут) и настоящий сервис команд с TimeProvider: запуск и доступность, очередь 100 мин, работа 20 мин, пауза 120 мин, возобновление и ещё 10 мин работы. Сохранённый итог: очередь 100, работа 30, всего 130, превышение нормы 90 мин — 40. Следующий шаг получает норму при доступности. Изменение текущей модели не меняет сохранённые 90 минут; отмена останавливает очередь следующего шага. Управляемые часы не подменяют системные настройки или время других сервисов.

tools/verify-execution-timing-http.mjs создаёт отдельную демо-копию, масштабирует даты примеров относительно среза и записывает только временные экземпляры. Настоящий API проверяет пять записей: три превышения (очередь, факт к отмене, завершённый факт), один текущий InProgress, один завершённый шаг, среднее 60 минут, UTC-срез и запрет аналитики исполнителю. Старая отменённая запись с CompletedAt не считается успешным циклом. Файл выполнений не меняется. Успешные прогоны: artifacts/execution-timing-http-lZepWj/report.json и финальный artifacts/execution-timing-http-Yikny3/report.json, по 5 проверок; оба сервера автоматически остановлены.

React-проверки охватывают неизвестный норматив, экранирование, подписи единиц, обновление очереди, остановку таймера на паузе, дату серверного среза и отбрасывание позднего ответа. Визуальная проверка браузером не заявляется.

Финальный общий прогон: 747 серверных сценариев и 356 клиентских проверок — успешно. Сборка успешна, основной модуль 469.66 кБ, крупнейший 572.16 кБ, порог 600 кБ не повышался.

Воспроизведение: из корня dotnet run --project backend/ProcessNavigator.Checks -c Release; затем node tools/verify-execution-timing-http.mjs. Из frontend/process-navigator-ui: node --test tests/*.test.mjs и pnpm build.

Формат сохранённых экземпляров не мигрируется. Данные и нормы не пересчитываются массово и не переписываются при чтении. История итераций, отдельные календарные планы и факты передачи остаются раздельными.
